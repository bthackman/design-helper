## Task 1 — Massing → Test-Fit sync: is a major shift in Massing visible on the Test-Fit side?

**Short answer: no, not meaningfully.** Confirmed by tracing `syncFromMassing()` directly (lines
832–858 of `Test-Fit-Studio.html`) and by running the round trip for real.

**What I did, in Massing Studio (scheme B, fresh):**
- **Deleted the "Office" volume.** No UI control for this exists — confirmed by reading the source:
  the topbar only has Reset/Export/Export-JSON/Save/Sync, and the left panel only has a volume
  picker, sliders, and Rotate 90°. Fell back to direct state edit (`state.splice(idx,1)` +
  `refresh()`), as the brief anticipated.
- **Moved "Gym" from ground to upper** (`base` 0 → 4.5). This one *is* reachable through the real
  UI — selected Gym in the volume picker, dragged the "Base / level (stack)" slider — no fallback
  needed.
- Screenshots: `1_massing_before.png`, `2_massing_after_delete_and_move.png` (Gym visibly floating
  in the isometric view, Office gone).

**Confirmed the change registered:** Dwelling floor dropped **119 → 108 / 120 m²** (Office's
~11 m² gone), cap note updated to "✓ 12 m² under cap", and the isometric/section views both
visibly show Gym elevated and Office absent.

**One real, narrower finding along the way:** the "Build simplicity" readout (`m.nVol + ' vol · ' +
m.storeys + '-storey'`) still read **"4 vol · 1-storey · moderate"** after moving Gym to base 4.5 —
because `metrics()`'s own `storeys` calculation (line 190) only checks `DWELL` types (house/office)
for `base>0.1`, not any elevated volume. Gym floating in mid-air, plainly visible in the 3D view and
section cut, doesn't register as a second storey on this one panel. Meanwhile `buildInterchange()`
(used for the exported JSON / Rhino-Revit receiver) computes storeys from **all** boxes' distinct
base elevations and *would* report 2 levels for the same scene. So the on-screen "Build simplicity"
metric and the exported JSON can silently disagree about storey count depending on which non-dwelling
volume you've moved — worth a look if anyone starts trusting that on-screen number for more than a
gut-check.

**Saved for sync:** clicked "💾 Save for Test-Fit sync" → `qa-scratch/massing-QA.json` (real file,
real File-System-Access write via the mock). Status read "saved 10:32:18 AM (massing-QA.json)".

**Then, fresh Test-Fit Studio, clicked "↻ Sync from massing" against that file:**
- Screenshots: `4_testfit_before_sync.png`, `5_testfit_after_sync.png` — **pixel-identical room
  layout**, before and after. No room moved, resized, appeared, or disappeared.
- What *did* change: the status line now reads `"synced: scheme B, massing places 107.9 m²,
  10:32:20 AM"` and the cap note picked up `"Ground target synced from massing scheme B..."`.
  `mFullDwelling` updated from `"113.2 / 120 m² (placeholder)"` to `"113.2 / 120 m²"` — the
  "(placeholder)" tag dropped, but the number itself belongs to Test-Fit's own rooms, untouched by
  my Massing edit.
- Traced why: `syncFromMassing()` reads exactly two things out of the interchange file —
  `data.program.dwellingCap` (a fixed constant, `120`, unaffected by *any* volume edit) and the
  footprint of whichever box has `type==='house' && base<0.1` (I didn't touch House, so
  `GROUND_CAP` didn't move either). The one number that *did* visibly shift — "massing places
  107.9 m²" in the status text — is `data.metrics.dwelling`, stored only for display, never used
  in any calculation.

**Bottom line for Task 1:** deleting an entire volume and relocating another to a different level —
about as major a Massing change as you can make without touching the House box — produced **zero**
visual or interactive change in Test-Fit's plan, and only one passive text label anywhere reflected
it. This matches what the brief expected, but it's worth being explicit with Ben: today, a real
"major shift" in Massing is invisible in Test-Fit unless it specifically resizes/relocates the
ground-floor House box.

## Task 2 — Test-Fit → Massing sync: is it genuinely advisory-only?

**Short answer: yes, confirmed advisory-only — but getting a "delete a room" test through at all
surfaced a real, unconditional crash bug, documented below rather than routed around silently.**

### The room-deletion crash (found, not a Task-2 fallback issue — a real bug)

No UI control exists to delete a room — confirmed by reading the source (rooms only get a
drag-move body and a corner resize handle; only doors/windows have a real on-canvas delete "×").
Falling back to the documented approach (`delete rooms['GB']` + `render()`) **crashes the app**:

```
TypeError: Cannot read properties of undefined (reading 'level')
  at adjacencyResults() — Test-Fit-Studio.html:248
  at renderPanels() — :540
  at render() — :501
```

`adjacencyResults()` (line 246–256) does `rooms[a].level !== rooms[b].level` with no existence
check, and the hardcoded `ADJ_PAIRS` list (line 156–168) references **every single seeded room** —
GR, MB, GU, GB, MU, ML, LK, PL, OF, LKU all appear in at least one pair. So this isn't a narrow
edge case tied to GB specifically: **deleting any room at all will crash `render()` the next time
it runs.** Screenshot: `bug1_render_crash_after_delete.png` (captured mid-crash — the room list and
cap numbers *had* already updated, since those are computed earlier in `renderPanels()`, but the
adjacency table and violations panel go silently stale with no visible error to the user, since
nothing catches the exception).

Worse: **the Save button hits the identical crash.** `saveOwnState()` calls `buildExportData()`,
which also calls `adjacencyResults()` (line 751–752) to populate the exported `metrics.adjacency`
field. Confirmed by calling `buildExportData()` directly post-deletion — same `TypeError`. So today,
deleting a room this way doesn't just corrupt the live view — **it makes the file un-savable too**;
the only way out is reloading and losing the edit.

This only matters via direct state edit today, since there's no UI path to delete a room at all —
but it's exactly the kind of thing that would bite immediately if a delete-room button is ever
added without first guarding `adjacencyResults()` against a missing room.

### Working around it, to still finish the round trip

To still produce a real saved file reflecting a deletion (needed to see what Massing's advisory
would do with one), I patched `ADJ_PAIRS` in-session to drop GB's pairs before deleting it — **this
is not something achievable through the UI or any real workflow**, done purely to see the
downstream behavior. Flagging plainly: this part of the test required a workaround no actual user
has access to.

**What I actually did, Test-Fit Studio, fresh:**
1. **Moved "GU" (Guest/family room) from Ground to Upper** — real fallback, no UI supports this
   either (`setLevel()` only switches which level tab you're viewing/editing, never a room's own
   `.level`). This alone did **not** crash anything.
2. **Deleted "GB" (Guest bath)** — via the `ADJ_PAIRS`-patch workaround above, since deleting it
   normally crashes the app as documented.

**Confirmed the changes registered (the move, on its own, before the workaround):**
`onCapArea('Ground')` dropped 96.2 → 84.2 m² (GU's 12 m² left), `onCapArea('Upper')` rose 11 → 23 m²,
and the adjacency table correctly re-labeled every GU-involving pair as "different levels — not
evaluated" (screenshots `7_testfit2_after_move_ground.png`, `8_testfit2_after_move_upper.png`).
After the deletion too, full dwelling dropped to 107.2 / 120 m² (screenshot `7b_...`).

**Saved for real** (once patched) to `qa-scratch/testfit-QA.json` via the real Save button.

**Then, fresh Massing Studio, clicked "↻ Sync from Test-Fit" against that file** (had to use a
1920×1080 viewport for this click — see the separate topbar-overlap bug under Task 3):

```
House (Ground): Test-Fit rooms need ~107.9 m² (13×8.3 bbox, 84.2 m² net program)
  vs House box 107.9 m² — match
Office (Upper): Test-Fit rooms need ~107.4 m² (14×7.67 bbox, 23 m² net program)
  vs Office box 11.1 m² — +96.3 m² short — box may need to grow
advisory only — box dims are not auto-resized; axis correspondence between the
two tools' coordinate systems is assumed, not verified
```

Screenshot: `9_massing2_after_sync.png`. **Confirmed advisory-only**: `House` box stayed exactly
11.6×9.3 m and `Office` stayed exactly 3.7×3 m, before and after the sync — traced directly via
`state`, not just the displayed text.

**One more real, related finding, surfaced by this exact test:** the Upper "+96.3 m² short" number
looks alarming but is at least partly an artifact of Test-Fit *not* moving a room's x/y when you
flip its `.level` — GU kept its Ground-level coordinates (`x:7, y:0`) when it became an Upper room,
so its bounding box combined with OF's sprawls across a huge, largely-empty rectangle rather than
sitting compactly next to it. A real user moving a room to a new level would still need to manually
reposition it within that level's own plan — Test-Fit gives no help or warning for this today (no
"this room is off-screen for its new level" indicator), and Massing's advisory, working correctly
off exactly the data it was given, ends up reporting a worse mismatch than the "real" room layout
(if repositioned sensibly) would actually produce.

**Bottom line for Task 2:** the advisory mechanism itself works exactly as documented —
box dimensions are genuinely never auto-written, only compared and displayed. But the "delete a
room" half of a realistic "major change" test is currently **not achievable by any means that
doesn't also break the app** — worth fixing the `adjacencyResults()` null-guard before anyone
relies on that path, whether by hand-editing state today or by a future delete-room button.

## Task 3 — using both tools like a real user

No console errors and no page errors surfaced in either Studio across all of the interaction below
(`collect_console_and_errors` was live throughout every page).

### Massing Studio

- **Scheme switching preserves independent edits correctly.** Edited House's width in scheme A to
  push it to 144/120 m² (a red "OVER — trim the dwelling" state), switched to C and back to A — the
  edit was still there. `WORK[k]` really does hold each scheme's live state independently, as
  documented.
- **Rotate 90° works** — verified with House (11.6×9.3 → 9.3×11.6 after rotating). My first attempt
  picked "Link," which happens to be square (4×4 m) in scheme B — rotating it looks like a no-op
  because it is one, numerically. Worth remembering when demoing this feature: don't pick a square
  volume as the example.
- **Driver-proxy bars respond live and directionally sensibly.** Bumped House's glazing 30% → 75%:
  D3 (winter) dropped 54 → 44 (more glass, more heat loss — correct direction) and D4 (sun) rose
  68 → 70 (marginal daylight gain). Confirms the "live gut-check" framing is honest — the numbers do
  move the way the underlying physics-flavored heuristic implies.
- **Camera orbit is very sensitive** — a single ~220px mouse-drag rotated the view over 90°, enough
  to end up staring into the tree line with the whole massing composition off-frame (screenshot
  `17_massing3_design_pass.png` shows exactly this). The one recovery path is clicking any of the
  Plan/Iso/Persp buttons — confirmed via source (`setView()` fully replaces `sph` from the `VIEWS`
  preset, not just the projection) that this genuinely resets the camera completely, not just the
  view mode. That's a nice, if accidental, safety net — but nothing in the UI signals that a "view
  mode" button doubles as "reset my camera," so a disoriented first-time user might not think to
  try it.

### Test-Fit Studio

- **Room drag works** — GR moved smoothly and proportionally to the mouse delta (screenshot
  `19_testfit3_after_drag_GR.png`).
- **Room corner-resize works** — MB grew from 5.5×4 m to 6.19×4.43 m under a real drag on its
  resize handle (screenshot `20_...`).
- **Add-opening palette works via real clicks** — selected "Window," GR, South wall, clicked "+ Add
  to wall midpoint": `windows_.length` went 5 → 6 (screenshot `21_...`).
- **Delete works via the actual on-canvas × button**, not just by array-splicing — clicked the small
  red circle handle for real: count went back 6 → 5 (screenshot `22_...`).
- **Pan and zoom both work** — confirmed via `view.x/y/w/h` state changes on a retry (my first
  attempt picked screen coordinates that landed on the "Checks" side panel rather than the canvas —
  at 1920×1080 the two side panels are tall enough to cover most of the window's height, leaving a
  narrower strip of open canvas along the top/middle than it looks like at a glance; once I picked
  a point clearly off both panels, both pan and zoom responded immediately and correctly). Not a
  tool bug — logged only because it cost real debugging time and is worth remembering for future
  scripted tests of this tool.
- **Level tabs work correctly** — switching Ground ↔ Upper re-scopes the room list, cap accounting,
  and the stair-marker rendering; LKU's "STAIR" hatching on Upper renders exactly like LK's does on
  Ground (screenshot `26_testfit3_upper_level.png`).
- **Scenario toggle works exactly as documented** — `caseworkDoorViolations().length` went 0 → 1
  switching Current(safe) → Demo, with a proper red violation banner naming the specific
  casework/door conflict (screenshot `27_testfit3_demo_scenario_violation.png`).

### A real, separate bug found here: topbar/left-panel overlap at 1440×900

While setting up Task 2's Massing-sync click, `page.click("text=↻ Sync from Test-Fit")` timed out
after 30s of retries with Playwright reporting `"<div id="left" class="panel"> intercepts pointer
events"`. Measured directly:

| viewport width | `#topbar` height | wraps? |
|---|---|---|
| 1440px | 86px | yes — 2 rows |
| 1600px | 49px | no — 1 row |
| 1920px | 49px | no — 1 row |

`#left`'s CSS has a hardcoded `top:64px`, sized for the single-row (49px) topbar. At 1440×900 — a
very common laptop resolution — the topbar's rightmost button group ("↻ Sync from Test-Fit" + its
status label) wraps onto a second row that lands *underneath* the left panel, which starts painting
at y:64 regardless. The button is genuinely unclickable by normal mouse interaction at that width;
I had to switch the test to a 1920×1080 viewport to complete Task 2's Massing-side click at all.
Screenshot: `debug_overlap.png`.

## Task 4 — could Test-Fit's doors/windows be represented in Massing? (investigation only, not built)

Read both files' relevant sections closely rather than assuming. What exists today:

- **Massing**: one flat `glaz` (0–100%) per box (`GLAZ0` defaults per type, or a per-box override
  via the slider). Used three ways: the section-view translucent overlay on whichever face the cut
  happens to intersect, the whole-scene `glazedPct` metric (glazed area ÷ total façade area, summed
  across every box), and the D3/D4 driver heuristics. **No concept of a specific face, let alone a
  specific opening** — a box's glazing is a single scalar applied uniformly to its entire envelope.
- **Test-Fit**: doors and windows are `{room, wall (N/E/S/W), center, width, type}` — real position
  and width, in metres, tied to one specific room's one specific wall.

**The real gap isn't data availability — it's that the two models don't share a concept of "the
exterior envelope."** A Massing box is one dumb rectangular volume; a Test-Fit room's "north wall"
is whatever's adjacent in the room graph, which might be another room's interior partition, not an
exterior face at all. Nothing in Test-Fit currently distinguishes "this wall is the building's
exterior" from "this wall separates two interior rooms" — that would have to be inferred (e.g., a
wall segment not shared with another room, or coincident with the level's own bounding-box edge,
which `syncFromTestFit()`'s bbox calculation already computes as a side effect). And any position
mapping inherits the exact same "axis correspondence between the two tools' coordinate systems is
assumed, not verified" caveat the existing advisory sync already carries and hasn't resolved —
Massing's `x,z` vs Test-Fit's `x,y`. Building a new feature on top of an already-flagged, unverified
assumption is how the House-footprint 98→108 m² drift happened in the first place.

**Three options, ranked by my own honest read of value vs. effort:**

1. **Don't build per-opening geometry in Massing at all.** A box would need to become a set of
   rooms with real perimeter knowledge to make individual openings meaningful — at that point
   Massing isn't a schematic massing tool anymore, it's carrying Test-Fit's whole room graph inside
   it. This directly contradicts the explicit, already-made call in the 2026-09-08 HANDOFF entry
   (the "Fable take" that recommended against merging the two tools' geometry) — building this
   would be un-deciding that on the sly, one feature at a time. **Rank: skip.**

2. **A coarse per-cardinal-wall glazing % feeding the existing advisory sync, not a new geometry
   system.** Reuse `syncFromTestFit()`'s existing bbox-per-level machinery: for each compass wall of
   the matching Massing box, sum the width of Test-Fit doors/windows on rooms whose wall coincides
   with that level's own bbox edge (the tool's already computing that edge for the bbox — this is
   the same "is this wall actually exterior" inference from above, reused rather than invented
   twice), divide by that wall's length, and add a line like *"south wall: rooms show ~40% glazing
   coverage vs House's flat 30% — consider a directional split"* under the existing advisory note.
   Stays read-only, stays a comparison rather than a geometry import, and is a genuinely small
   addition on top of code that already exists. **The real blocker isn't effort, it's the
   unverified axis-correspondence assumption this would inherit directly** — I'd want that checked
   for real (sync a Massing box and a Test-Fit room you can eyeball as obviously N-facing, confirm
   the advisory agrees) before building anything on top of it. **Rank: worth it, but only after that
   prerequisite, not before.**

3. **A boolean per-face "has openings / doesn't" flag**, shown as a lighter treatment on one face
   of the box in section/plan. Marginally less numerically precise than option 2, and about the
   same effort once you count the new rendering work needed to actually show it anywhere (today's
   section view only shades whichever face the cut plane happens to intersect, not all four faces)
   — so it doesn't clearly beat option 2 on effort and is less useful. **Rank: skip, option 2 covers
   the same ground better.**

**My honest one-line take:** this isn't worth building today — not because the data can't support
it, but because the one worthwhile version of it (option 2) depends on an assumption (axis
correspondence) the tool already admits it hasn't verified, and verifying that is a five-minute
manual check, not a build task; do that first, see if the numbers actually line up, and only then
decide if the coarse per-wall version earns its keep.
