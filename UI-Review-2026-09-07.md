# UI Review — 2026-09-07

Four parallel agent passes on `_UI/Project-Window.html` and on tool-wide product direction, run at Ben's
request against the brief: this should feel like an actual professional tool — a terminal for
AI-assisted architecture work — not a generic web form or rough prototype. Two are text critiques (visual
design lens, UX/tool-builder lens), one is a product-direction recommendation, one is an actual redesigned
mockup built with Claude Code's `design` skill. None of these made code changes — they're inputs to a
future build session, not a build session themselves.

**Mockup artifact:** https://claude.ai/code/artifact/28ebd6a2-52b6-47b9-9c46-a8b321bd4cb7 — "Project Window
Redesign," both real screens (gate + dashboard) redesigned side by side with representative sample content.
Dark-first warm-charcoal palette with a bronze accent, IBM Plex Mono + Sans pairing (mono for
identifier-like content, sans for judgment content), header rebuilt as real app chrome, conscience panel
styled like an IDE problems panel, drivers-lock gate given its own visual register. Static, not wired up;
only the dark theme was designed. Sample content is invented, not from a real project.

## Where the two text critiques agreed

- Severity/status signaling leans on color alone (conscience panel rows, blocking-question text) — no
  icon, border, or fill backing it up.
- The native `<select>` project switcher and raw Unicode glyphs (▮▯✓⚠▼) are the clearest "unfinished"
  tells inside an otherwise custom-styled UI.
- The drivers-lock gate — the single most consequential state in the tool's mental model — is visually
  under-weighted (a 2px rule at list-row font size).

## 1. Graphic design review

Reviewed the full file (`_UI/Project-Window.html`, 643 lines) — CSS block (lines 6–98), gate/app markup
(100–165), and the JS that renders into it. No files edited; this is a code-level critique reasoning about
rendered appearance, since no browser was available to confirm pixel results.

### Strengths worth preserving

1. **A real color identity, not a default one.** Light tokens (`--bg:#faf9f6`, `--line:#ddd8cc`,
   `--accent:#8a6d3b`, lines 9–11) land on warm cream/tan/ochre rather than generic SaaS blue-gray. That's
   a legitimate "drafting paper / architect's studio" register and is the single strongest asset in the
   file — it already differentiates this from a bootstrapped web form.
2. **Genuinely custom status dots.** `.dot` (lines 53–57) draws complete/in-progress/not-started/
   looping-back states with actual CSS (border color, solid fill, a 50/50 `linear-gradient` for
   "in-progress") rather than an icon font or emoji. This is the one piece of iconography in the file that
   reads as *designed* rather than placeholder.
3. **A coherent semantic triad.** Red/amber/green (`--red/--amber/--green`) is reused consistently across
   phase dots, conscience severity rows, blocking-question text, and staleness badges — one status
   vocabulary, not several competing ones.
4. **Monospace used with intent.** `ui-monospace, Consolas` is reserved for genuinely "raw" content — the
   gate log, error output, raw-markdown editor, inline code (lines 20, 70, 118, 86) — which reinforces the
   "terminal for AI-assisted work" framing rather than using mono decoratively.
5. **Dark mode is a real second token set** (lines 12–14), not a filter/invert hack, and `color-mix()`
   (lines 51–52) for hover/current tints is a modern, systematic approach to state color rather than
   hand-picked new hex values.
6. **Density is appropriately tight** for a professional instrument rather than a spacious consumer app —
   driver cards, list rows, and the conscience panel all favor compact information display over whitespace
   padding, which is the right instinct for this brief.

### Weaknesses (ranked by cost to the "professional tool" bar)

1. **The native, unstyled `<select>` in the header.** `header select { font:inherit; padding:.3rem .5rem; }`
   (line 23) leaves the project switcher as bare OS chrome dropped directly into an otherwise custom
   header. The first interactive element a user sees is the one piece of UI that visibly did *not* get
   designed.
2. **The drivers-lock gate is under-weighted relative to its importance.** `.lock-gate` (lines 58–60) is a
   thin 2px horizontal rule with 11.5px dim text, only distinguished when locked by `font-weight:700`. The
   single most consequential state in the tool's mental model currently has less visual weight than a
   driver card.
3. **Severity/blocking signaling is color-only.** `.conscience .row.high/.medium/.low` (lines 43–45) and
   `.qlist li.blocks-now` (line 68) change text color and nothing else — no border, fill, or icon. Weakens
   at-a-glance scanning, fails for colorblind users, and works directly against "does the eye land on what
   matters."
4. **Raw Unicode glyphs standing in for icons.** `&#9646;/&#9647;` (lock gate, lines 331–332), `&#10003;`
   (clean conscience, line 393), `&#9888;` (high severity, line 403), `&#9660;` (collapse chevron, line 156)
   render at whatever weight the OS's symbol font happens to use — inconsistent with the deliberately flat,
   custom-drawn dots elsewhere. Exactly the "placeholder from the character map" tell.
5. **No governed type scale.** Sizes in use: 10, 10.5, 11, 11.5, 12, 12.5, 13.5, 14px — eight distinct sizes
   in a 4px band with no discernible ratio logic. Reads as accretion over many small edits, not a
   considered scale.
6. **No governed spacing scale either.** Padding/gap values scattered across .15/.25/.3/.35/.4/.5/.6/.75/
   .9/1rem with no 4/8px logic behind them.
7. **The primary heading is barely a heading.** `.proj-title { font-weight:700 }` (line 24) at the base
   14px body size means the project name — the "you are here" anchor of the whole app — is only
   distinguished by weight, not scale.
8. **Rail navigation isn't pinned.** The whole `.rail` (line 30) is one `overflow-y:auto` region holding
   Phases, Drivers, Open Questions, Decisions, and Close-out stacked in a flex column. As drivers/decisions/
   questions grow, the Phases list — the primary navigation — can scroll out of view with no sticky
   treatment.
9. **Dark-mode semantic colors are unexamined.** The dark media block (lines 12–14) redefines
   `bg/panel/line/text/dim/lock` but not `--red/--amber/--green/--accent`. Those were tuned for contrast
   against a cream background and now carry over unchanged onto a near-black one. **[verify live]**
10. **Inconsistent "badge-worthy" treatment.** The driver-lock indicator gets a real pill (`.badge`, line
    97), but the header's staleness/dormant/complete indicators (`#stateBadge`, `#sinceBadge`, lines 27–28)
    are plain colored text with no shape.

### Prioritized recommendations

**High priority**
1. Restyle the project `<select>` (CSS line 23, markup line 113): `appearance:none`, custom border, custom
   chevron, padding matched to the rest of the header controls.
2. Give the drivers-lock gate (CSS lines 58–60, JS lines 326–334) real visual weight: full-width
   banner-style treatment, a filled state chip when locked, a proper icon rather than a 2px rule.
3. Reinforce severity/blocking states with more than color: left border stripe or subtle background tint
   on `.conscience .row.high/.medium` (lines 43–45) and `.qlist li.blocks-now` (line 68), paired with a
   consistent icon glyph.

**Medium priority**
4. Replace the bare Unicode glyphs (lines 331–332, 393, 403, 156) with a small shared inline-SVG icon set
   at one consistent stroke weight, matching `.dot`'s 1.5px border weight.
5. Collapse the type scale to 5–6 deliberate steps (e.g. 11/12/13/14/16/20px); give `.proj-title` a real
   size jump (18–20px).
6. Normalize spacing onto a 4px-based scale (4/8/12/16/24px) across driver-card, conscience rows,
   qlist/declist, form.append.
7. Make the Phases section sticky within `.rail` (or split into a fixed nav zone + independently-scrolling
   content zone).

**Low priority**
8. Explicitly redefine `--red/--amber/--green/--accent` inside the dark-mode media block for a dark
   ground.
9. Extend `.badge` pill treatment to `#stateBadge`/`#sinceBadge`; consider a small monospace chip for the
   driver "D1" numbering.

### Flagged for visual confirmation (can't verify from code alone)

- Actual contrast ratios of `--dim` on `--bg`/`--panel` at 11–12px in both themes.
- Whether amber/green/red read clearly against dark-mode `--bg`/`--panel` or look muddy.
- Exact per-OS rendering of the native `<select>` and of the Unicode glyphs.
- Whether the 10px "in-progress" half-gradient dot is legible as a half-fill at that size.

## 2. UI/UX and tool-builder review

Read in full: `_UI/Project-Window.html` (642 lines), `_UI/spine-parse.js` (307 lines), `_UI/audit.js` (132
lines), `README.md`. Static-code read — no live browser available — so anything marked **[verify live]**
should be confirmed by actually running it before trusting this read.

### Strengths worth preserving

1. **Offline-first, dependency-free architecture is exactly right for this tool.** No CDN, hand-rolled
   markdown renderer tuned to the spine's actual dialect instead of a generic library
   (`Project-Window.html:502-513`).
2. **Two genuinely different conflict strategies, chosen deliberately.** Full-doc raw-markdown save uses
   re-read-and-confirm (`:484-493`); decision-log append uses re-read-and-splice at a located insertion
   point (`:590-611`), with an inline comment explaining why they differ.
3. **`reconcile()`'s defensive layering** (`spine-parse.js:263-293`) — falling back to `inferState()` when
   `state.json`'s schema doesn't match, documented against a real production incident.
4. **The drivers-lock gate rendered as a literal marker inside the phase list** (`:326-334`) rather than a
   separate legend — visualizes the workflow's actual non-linear shape directly where you'd look for it.
5. **The conscience panel's caveat text and dedup discipline.** `changedSinceLock` collapses N hits into
   one finding ("a panel that lists four rows for the same concern trains you to ignore it," `audit.js:
   69-71`). The one-line summary count stays visible even when the panel is collapsed.
6. **Requesting `mode: 'readwrite'` up front** (`:623`) avoids a second permission prompt later.

### Weaknesses

**Onboarding/gate**
- Failure path is generic: `for (const w of want) await repoHandle.getDirectoryHandle(w)` (`:625`) throws
  on the *first* missing folder with no indication of which one; the catch just logs raw
  `e.name + ' — ' + e.message` (`:637`).
- **No persisted directory handle.** No IndexedDB storage of the picked `FileSystemDirectoryHandle`, no
  `queryPermission`/`requestPermission` re-use — every session starts with the picker again. For a tool
  meant to be opened daily, this is the single biggest "form, not terminal" tell.
- Auto-loads the alphabetically-first project (`:635`) rather than the last one you had open.

**Left-rail information architecture**
- **Decisions are silently truncated**: `.slice(0, 8)` and `.slice(0, 140)` chars (`:381,383`) with no
  "view all" link — for a tool whose entire premise is a durable decision trail, clipping without an
  escape hatch undercuts the core value prop.
- **One shared scroll region for five unrelated sections** (`.rail{overflow-y:auto}`, `:30`) means a long
  list can push the phase list — the primary navigation — off-screen.
- Open-questions list has no cap and no grouping beyond a single red/plain color split (`:361-375`).

**Phase rail as workflow visualization**
- **The rail's "current" highlight never reflects what you're actually looking at.** `.phase.current` is
  driven only by `parsed.state.currentPhase` (`:337`); `openPhase()` (`:435-455`) never updates any
  "selected" state or re-renders the rail. Click through phases and the highlight never moves.
- **`looping-back` may be unreachable in practice.** The CSS/status vocabulary includes it (`:57`), but
  `inferState()` — the fallback used whenever `state.json` is missing or mismatched — only ever assigns
  `'complete' | 'in-progress' | 'not-started'` (`spine-parse.js:243-252`). **[verify live / verify
  skill-side]**
- No tooltip/title text on the status dots (`:338`) — color is the only signal.

**Conscience panel**
- No per-finding dismiss/mute and no click-through to the flagged driver/question/card.
- **Collapse state is global** (`localStorage['pw-conscience-collapsed']`, `:411-415`), not per-project —
  collapsing it while looking at one project silently suppresses it for the next project too.
- "Low" severity rows use the same dim gray as ordinary UI chrome (`--dim`) — the tier meant to reward a
  careful glance is the one most likely to visually disappear.

**Edit-in-place / conflict handling**
- **`alert()`/`confirm()` for routine save feedback and conflict resolution** (`:487, 492`) are the
  sharpest "prototype" tell in the file — no professional tool blocks the page with a native dialog for a
  successful save, and the conflict dialog offers only "Overwrite anyway?" with no diff.
- After a successful save, the doc stays in raw-editor mode — no switch back to rendered view.
- The decision-append's divider lookup (`:603`) grabs the *first* markdown-table divider in the file
  rather than reusing `readDecisions()`'s stricter column-matching logic (`spine-parse.js:180`) — risk of
  inserting into the wrong table if the log ever grows a second table.

**Massing Studio iframe**
- No `postMessage` bridge either direction — the outer app has zero visibility into Studio activity until
  a full reload, and the Studio can't learn the outer app's theme. Regenerated fresh on every
  `openPhase('massing')` call (`:438-446`), so any pan/zoom position is lost when you glance away and back.
  **[verify live: whether Studio persists state to disk or only in memory]**
- No pop-out/fullscreen affordance for a rich interactive tool squeezed into a rail-constrained pane.

**State management**
- Three different trust signals (dormant/complete, schema-mismatch/stale, "N files changed") crammed into
  small `.since`-styled header spans with only amber/red text as differentiation.
- When `state.json`'s schema *is* valid, its claimed phase statuses are trusted at face value even if
  stale by mtime (`spine-parse.js:292`).

**Where this reads as prototype vs. tool:** native `alert`/`confirm` dialogs, zero keyboard shortcuts
anywhere, no search/command-palette across drivers/decisions/questions/phase text, no resizable rail, no
persisted folder-handle/session resume, rail's "current" indicator not tracking what's on screen. The
underlying data model and reconciliation logic are notably more mature than the interaction layer
presenting them.

### Prioritized recommendations

1. **Kill `alert()`/`confirm()`.** Inline toast for save-success; an in-app conflict view instead of a
   blocking confirm. `:487, 492`.
2. **Persist the directory handle** (IndexedDB) and re-request permission on load. Highest-leverage fix
   for "feels like a tool I live in."
3. **Sync the phase-rail highlight to whatever's actually open** — track a `selectedPhase` in `openPhase()`
   and re-render the rail against it. `:322-342, 435-455`.
4. **Un-clip the decision log** — remove/raise the `.slice(0,8)`/`.slice(0,140)` limits or add a real
   "view full log" path. `:381,383`.
5. **Give the rail independent scroll/collapse per section.** `:30`.
6. **Make conscience-panel collapse per-project**, and/or force-expand when high-severity findings exist
   regardless of stored state. `:411-415`.
7. **Add click-through + per-finding mute to conscience findings.**
8. **Fix the decision-append divider lookup** to reuse `readDecisions()`'s column-matching logic. `:603`
   vs. `spine-parse.js:180`.
9. **Add baseline keyboard support**: navigate phases, Ctrl/Cmd+S to save, Esc to cancel.
10. **Add lightweight cross-project search** over drivers/decisions/questions/phase text.
11. **Confirm `looping-back` is actually reachable** from the skill's `state.json` writes.
12. **Add `title=` tooltips (and a text label) to phase-status dots.** `:338`.
13. **Bridge the Massing Studio iframe** with at minimum a `postMessage` "files changed" ping, and pass
    the current theme in.
14. **Return the doc to rendered view after a successful raw-markdown save.** `:492`.
15. **Remember the last-opened project**, not just per-project last-opened timestamps. `:635`.

## 3. Product-direction recommendation: build the Test-Fit Studio next

### The pick

Build the interactive **Test-Fit Studio** for Space Planning — a client-side HTML tool mirroring the
Massing Studio (live room-block placement sized to program areas, door/opening markers, and a live
circulation-clearance + adjacency check) — as the next thing built in this tool.

This is already named as the next tooling target in three places (`HANDOFF.md`, `Tool-Strategy-Map.md`,
backlog row #20), so the case isn't "found something nobody noticed" — it's that this item beats every
other open item on a real cost/benefit basis, and there's now a piece of evidence on disk that sharpens the
case beyond when it was first flagged.

### Why it beats the alternatives

**It beats the export pipeline.** `SKILL.md`'s Exports section (lines 234–241) already delegates to
generic file-creation skills rather than describing bespoke code. "No export pipeline exists" is largely
an unexercised wiring/formatting question, not a new interactive artifact — real but low-risk, low-
engineering, and doesn't change how design work gets *done*, only what leaves the tool at the end.

**It beats the Rhino receiver / Blender polish.** These only matter once a project has actually pushed a
real massing-interchange export downstream — and the one real (synthetic) project on this machine,
Nyando, explicitly *skipped* building the interactive Massing Studio, judging the 3D/Three.js build
disproportionately expensive. Investing in a third CAD receiver before the second Studio even exists
optimizes a pipeline stage nothing is currently feeding.

**It beats Materiality library promotion and "run on a real client engagement."** Both are blocked on
things a build session can't manufacture — a completed built project, and an actual client.

**It beats spine version-history / gitignore fragility.** Real risk, but already surfaced and explicitly
*declined* by Ben when the "dream pass" flagged it (HANDOFF, 2026-09-06).

**Why it beats leaving Space Planning as prose — the strongest, evidence-based argument.**
`Projects/Nyando-Maternity-Waiting-Home/4_Space-Planning/Program-Test-Fit.md` — a real (synthetic) run of
the current manual method — surfaced two genuine, load-bearing findings purely from doing the arithmetic
and matrix-checking by hand:

1. A **required adjacency violated across clusters** (newborn stabilization nook and night-nurse room are
   matrix-required-adjacent but massing put them in different clusters) — found only after massing was
   already locked.
2. A **veranda depth undersized** once real door count and the population-appropriate 1.2m clearance band
   were traced — found only "by the furnishing exercise the massing phase itself doesn't run."

Both are exactly the class of error a live collision/adjacency check would catch *while placing volumes*,
not after the fact in a markdown table — the same "steer, don't just pick" thesis the Massing Studio
already proved, applied to the phase where Ben will spend the most real hours on an actual project. It's
also **cheaper to build than the thing it mirrors**: Test-Fit is fundamentally 2D (canvas/SVG, rectangles,
geometry checks on line segments), no Three.js, 3D volumes, or sun-angle math needed.

### What v1 should actually be

**Format:** single self-contained `Test-Fit-Studio.html` (Canvas/SVG + vanilla JS, no 3D library),
`file://`-openable, generated per-project into `4_Space-Planning/`, linked from `Program-Test-Fit.md` the
same way Massing Studio is linked from `Massing-Options.md`.

**Reads:** the program table and adjacency matrix out of `Program-Test-Fit.md`; the massing footprint out
of the Massing Studio's `massing-interchange/v1` JSON **if it exists**, but don't hard-require it — Nyando
shows the Studio export won't always exist. v1 needs to work as a freeform test-fit sketchpad (rooms as
resizable/draggable blocks sized to their NSF, no forced outline), with an optional floor-outline overlay
when a real export is available.

**Always-build-in, client-side:**
- Room blocks sized/labeled from the program table, draggable/resizable, grouped by cluster, with a live
  per-room NSF readout and a running total-GSF-vs-massing-cap meter (same cap-meter pattern as Massing
  Studio).
- Click-to-place door/opening markers per room wall, each drawing its clear-swing arc.
- Live desire-line + keep-clear-band computation between openings (0.9m/1.2m/1.5m per
  `phase-4-space-planning.md`'s existing rule), flagging any furniture/casework intrusion.
- Fixed-casework flag: a block tagged "fixed" that isn't fully on a solid, opening-free wall run lights up
  red.
- A live adjacency panel: reads the matrix, checks actual block-to-block proximity/clustering, flags
  violations in real time — the piece that would have caught the newborn-nook/night-nurse conflict during
  placement.
- Export JSON (`test-fit-interchange/v1`, mirroring the massing export's pattern).

**Deliberately deferred:** multi-floor stacking, AI-suggested layouts, a real furniture catalog beyond
simple rectangles, non-orthogonal room shapes. v1 stays at the same schematic abstraction level the phase's
own deliverable already uses.

**What "done" looks like:** generate `Test-Fit-Studio.html` against Nyando's actual
`Program-Test-Fit.md`/`Massing-Options.md` (already on this machine) and confirm it either reproduces the
veranda-clearance and cross-cluster-adjacency findings live, or at minimum doesn't miss anything the
manual pass caught.

### Risk / honesty

- Same validation gap as everything else: reviewed against one synthetic, solo-authored project, not an
  independent human pushing back on a real layout.
- Topological risk: space planning is more open-ended than massing's parametric boxes; a naive block tool
  could feel like a toy if real test fits are more organic than the schematic level this targets.
  Mitigation is scope discipline.
- Compounds an unvalidated pattern: Massing Studio has only fully round-tripped once (Nonimuss, no longer
  on this machine) — building a second Studio before the first is proven at scale is a real bet that the
  *pattern* generalizes, not just that it worked once. Mitigated by testing immediately against real local
  data (Nyando).
- Payoff condition: pays off specifically because Ben's real work involves iterating room layouts against
  clearance/adjacency rules by hand — if that's not where his actual time goes, the tool is a nice demo
  with less day-to-day pull.

## 4. Design-skill mockup — full agent report

Published the redesign as a two-artboard design canvas.

**Artifact:** https://claude.ai/code/artifact/28ebd6a2-52b6-47b9-9c46-a8b321bd4cb7

Contains both real screens from `_UI/Project-Window.html`, redesigned side by side:

- **Gate screen** — first-run "connect to a repo" dialog, restyled as a terminal-flavored connect panel:
  dashed drop-target around the folder-open button, a live-feeling verification log
  (`✓ _templates found`, `✓ Projects found — 4 project(s)`, etc.) in place of the plain log div.
- **Main dashboard** — header, phase rail, conscience panel, and viewer, populated with a full sample
  project ("Sorensen Residence — Coastal Infill"): phases in complete/looping-back/in-progress(current)/
  not-started states, the drivers-lock gate as a dash-dot "match line" marker between Site and Precedents,
  3 driver cards, 3 open questions (one tagged `[ BLOCKS: MASSING ]` in red), 2 decision-log rows plus the
  "+ log a decision" ghost affordance, a close-out link, a conscience panel with one high/one medium/one
  low finding (full-row severity coloring, plus icons), and a markdown-doc viewer rendering a Massing
  Options table/blockquote/next-steps as a bordered document card.

**Key design decisions**

- **Dark-first, warm-charcoal palette** (not the original's light-default) with a bronze/amber accent —
  reads as a persistent daily workspace (CAD tool, IDE) rather than a document or web form. Semantic status
  colors (green/amber/red) carried over from the original, recalibrated for dark contrast. A separate cool
  "steel" tone is reserved only for the drivers-lock gate, so that checkpoint visually reads as a different
  *kind* of thing than content.
- **Type pairing: IBM Plex Mono + IBM Plex Sans** — mono for anything identifier-like (file paths, dates,
  phase/driver tags, badges), sans for judgment content (driver text, decisions, findings, prose). This
  split is doing real information-hierarchy work, not just decoration.
- **Header elevated into real app chrome** — brand mark, a mono breadcrumb-style project path, and a badge
  cluster (since-last-open, stale, a live "workspace connected" indicator) so the header reads as a
  workspace's status bar, not a page title.
- **Conscience panel styled like an IDE problems panel** docked above the viewer; sharp corners and thin
  borders throughout, with colored left-borders/icons used only where they carry real meaning (blocking
  question, current phase, severity) — avoided generic rounded-card-with-accent-bar styling.

**Left unresolved / worth Ben's input**

- Built as **static mockups**, not a working prototype — the expanded decision-log form, the raw-markdown
  edit toggle, and the Massing Studio iframe are shown only as entry points, not functioning.
- Only the **dark theme** is designed; the original was light-first with a dark variant. Worth deciding
  whether dark becomes the default for this tool or stays an option.
- Sample content (project name, drivers, decisions, findings) is invented for demonstration, not from a
  real project.
- Didn't mock the all-clear/clean conscience state or the dormant/schema-mismatch badge variants.
