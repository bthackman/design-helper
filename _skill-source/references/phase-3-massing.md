# Phase 3 — Building massing

Output: `3_Massing/Massing-Options.md` — minimum three genuinely different options, scored, with a recommended direction logged as a decision — **plus an interactive Massing Studio** (`3_Massing/Massing-Studio.html`) that instruments the options so the architect can steer them, not just pick one.

## Generate wide first
Propose massing partis for the user to react to — bar, courtyard, tower-on-podium, terraced, split/linked volumes — filtered by the envelope from phase 2 and lessons from phase 1. Three options that share one parti are one option; force real difference (different section, different ground relationship, different organization).

## For every option, run the numbers
Footprint × storeys → GFA; compare to required GSF from the brief (with grossing factor); check against envelope (setbacks, height, FAR). Compute, don't estimate. An option that doesn't fit the program or the envelope is either dead or requires a logged decision to change the brief/seek variance.

## Score against drivers
Each option gets a driver scorecard (✓ / ~ / ✗ with one line of why per driver). This is where drivers earn their keep — if every option scores identically, the drivers are too vague, and that's worth surfacing. Where a score rests on the geometric proxy rather than a real test — the same honesty already required of the Studio's driver proxies — the rationale line carries `[proxy, unverified]` too, so the scorecard doesn't look more certain than the proxy behind it.

## Converge
Recommend a direction (an option or a named hybrid) with rationale. The user decides; the decision — including rejected options and why — goes to the decision log. Park, don't delete, the losers: mark status parked/dead so they're recoverable when the client asks "did you consider...?" Log the same call to `Library/Parked-Ideas.md` (project, option, why it died, reconsider-if) — that's what makes "have we tried this anywhere before" answerable across projects, not just within one.

**A promotion (see "Stage 1 → Stage 2" below) gets its own decision-log row, same table, no new columns.** Content: which volume, before/after dims, the triggering room-level conflict it resolved (or partially resolved — box-grow can leave a real gap unresolved, see the caption rule below). Because a promotion is genuinely cross-phase — it's *triggered* by phase 4 (a room placed against the volume) and *lands* in phase 3 (the volume's own `w`/`d`/`x`/`z`) — write its **Phase** cell as `"Space planning → Massing"` rather than a single phase name, the one convention every other row doesn't need since every other row lives in exactly one phase.

## Stage 1 → Stage 2 — siting, then articulation (2026-09-09)

The Massing Studio, as built, actually has two sub-stages living inside this one phase, not aligned to any phase boundary — worth naming so a future session doesn't mistake one for the other:

- **Stage 1 — siting.** A coarse, axis-aligned box per functional volume, sized and positioned to prove the program fits the envelope and the cap, pick a parti, and pass a sun-tested section. This is everything above in this document — nothing about it changes. In BIMForum LOD terms (the citable anchor for a client or licensure reviewer, since LOD is explicitly phase-independent, unlike AIA's SD/DD): **Stage 1 is LOD 100** — a conceptual mass establishing volume, area, height, location.
- **Stage 2 — articulation.** Once Test-Fit (phase 4) has placed real rooms against a Stage-1 volume, that volume can be **promoted**: a "Reshape to fit" action grows/repositions its box, on request, to the rooms' actual bounding box — a one-time, previewable, undoable commit, never a live binding. **This is box-grow only, never one-box-per-room** — the volume stays a single box; only its `w`/`d`/`x`/`z` change. That constraint is load-bearing, not stylistic: the moment a room becomes its own volume, `nVol` (and through it D3's volume-count term and D5) stop discriminating a genuinely complex scheme from a normal one — see the metric-gating rule below for the checked reasoning. A promoted box is **Stage 2 / LOD 200** — approximate geometry, still not a real assembly (LOD 300 would mean real polygon hulls and a new volume type; not built, not needed until a real project's promotion history shows the box-grow gap actually causing a wrong decision downstream).

**Metric-gating rule, so the Studio never computes on a stale box silently.** `metrics()`/`drivers()` stay exactly as built (a pure lift, never rewritten for this) — the gating lives in a separate `metricsDisplay(m, state)` wrapper that decides, per field, whether to show the raw number or a tagged sentinel, based on whether any COND-type volume (`house`/`office`/`pool`/`link`) in `state` carries a promotion:
- **Gated (shown as `[schematic-only — see Stage 2]`, using the tool's existing bracketed Judgment-flag convention):** `facade`, `effLoss`, `glazedPct`, and **D3** (winter thermal) — a promoted box's perimeter can understate real exterior wall once a room layout is articulated (a non-rectangular room cluster's bbox includes non-program notch area, the opposite direction of error from one-box-per-room's double-counting). The trade-space chart's D3 bar and the live ★ bubble's radius/color get the same greyed treatment; the A/B/C reference bubbles are always Stage-1-grade and never recompute.
- **Captioned, not hidden:** `coverage` (still one honest number, but now a conservative upper bound — the box includes any notch area) and `nVol`/build-simplicity (still arithmetically correct — box-grow doesn't inflate it — but now counts boxes, not rooms, so it silently under-represents how articulated a promoted volume's interior actually is).
- **Confirmed safe, no change:** the cap meter (filters by type, not box shape), D1/D2/D4/D5/CAP6 (none reads `facade`/`effLoss`/`nVol`). D2 legitimately *changes* when a promoted box's real gap to another volume changes — that's the metric correctly reacting to real geometry, not a distortion.

**The badge, not a tab.** Stage is a **per-volume provenance fact** (`state[i].promoted`), not a page-level mode — House can be Stage 2 while Pool stays Stage 1, and that's the honest common case, not an edge case (House gets rooms placed against it first; Pool/Office/Link may never need promoting if they were already sized to their real footprint). Surface it as a small label next to the volume's own entry in the picker/slider panel ("House — LOD 200" / "Stage 2 — LOD 200 (articulated) · promoted <date> · was <old dims>"), never as a new top-level mode control alongside the scheme/view/pane-layout switchers — those three are "how do I look at the same data," genuinely orthogonal; stage is "which numbers are currently trustworthy for one volume," a narrower per-object fact that a page-wide toggle can't represent once even one volume diverges from the rest. There is no "demote" button: a promotion writes `state[i]`'s dims the same way any slider edit does, so it's reversible the same way (drag it back, or reload a pre-promotion save) — the decision-log row above is the practical undo record.

## Room massing (live) — a third, distinct view, not a replacement for Stage 1/Stage 2 (2026-09-10)

A **live one-box-per-room mode**, added after an earlier, disconnected "3D room massing" viewer (built inside Test-Fit Studio, reading Test-Fit's rooms with no connection to Massing's own instruments) missed what was actually being asked for. Ben, on seeing that first attempt: *"Still not quite what i meant - because i wanted it to go back into the massing studio where sections and sun study etc is visible with the new massing."* This is **not** Stage 2 promotion above — it's a third, separate way of looking at the same Massing Studio, and the two must not be conflated:

| | Stage 2 promotion ("Reshape to fit") | Room massing (live) |
|---|---|---|
| Grain | One box per **type** (house/office/pool/link) | One box per **room** |
| Writes to `state`? | Yes — an explicit, previewable, undoable commit | **Never** — pure read, nothing is ever written |
| Trigger | A click, after reviewing a preview | Automatic — rebuilds on every Test-Fit `render()` |
| Decision-log entry? | Yes (see above) | No — nothing was committed, so there's nothing to log |

**What it is.** A topbar mode toggle in Massing Studio itself: "Schematic (Stage 1)" / "Room massing (live)". Switching to Room massing builds one 3D box **per Test-Fit room** — never aggregated by type or cluster, so a palette-added room (`R1`, `R2`...) gets its own box exactly like a hand-seeded one — fed into `drawSection()` (section cut + sun study) via a `withBoxes(boxes, fn)` swap-and-restore helper that substitutes the room-boxes for `state` only for the duration of one function call, then restores it. `drawSection()` itself, and `metrics()`/`drivers()`, stay byte-identical — nothing about them is rewritten for this mode; the substitution happens entirely at the call site.

**The one deliberate exception to "nothing auto-applies geometry" in this Studio.** Room massing rebuilds live, with no button and no preview-then-commit step, because nothing here is *ever* written back into the authoritative `state` array — there's nothing to accidentally commit, so the risk a click-gate exists to prevent doesn't apply. Stage 2 promotion keeps its click-gate; this mode never needed one.

**An honest subset of the instruments, not all of them.** Cap meter, lot coverage (captioned as a conservative reading), and enclosed volume carry over. Façade/`effLoss`/glazedPct, the driver-proxy panel, and the trade-space plot are **hidden** in this mode, not faked — one-box-per-room is exactly the grain the metric-gating rule above already exists to warn about (`nVol` explosion; façade summed across 12-15 small boxes instead of 4-6 large ones stops meaning what it means today). Don't re-enable these fields for this mode without first re-deriving what they'd even represent at room grain — this isn't a TODO, it's an open question that needs a real answer, not a default-on.

**Reachable from Project Window's phase rail**, not just by opening the file directly: the Massing phase tab carries a "Schematic (Stage 1)" / "Room massing (live)" sub-toggle. That route keeps **both** panes visible (Massing in Room-massing mode, left; Test-Fit's plan, right) — Ben, 2026-09-10: *"I want to see the plan and the 3D room massing at the same time."* This is the opposite default from the Schematic route, which hides Test-Fit's pane on purpose (Stage 1 siting doesn't need rooms visible to be steered); Room massing mode is specifically *about* the rooms, so hiding them would defeat the point.

**Only real once Massing Studio and Test-Fit Studio share a runtime** (a generated `Design-Studio.html`, below). A project with a Test-Fit Studio but no Massing Studio at all has no volumes to compare rooms against, so it falls back to Test-Fit's own standalone "3D room massing (standalone)" tab (see `phase-4-space-planning.md`) — a plainer one-box-per-room 3D preview with no section, sun-study, or cap meter, since there's no Massing Studio there to supply them.

## The merged runtime (`Design-Studio.html`) — build once both Studios exist for a project

Room massing (live), the promotion cross-call in phase 4's Test-Fit Studio, and the Step 0/5 live-ghost overlays all depend on Massing Studio and Test-Fit Studio sharing one runtime, not two files that occasionally sync a saved JSON. `iframe`s can't do this — Chrome (and every other tested browser) throws `SecurityError` scripting across `file://` frames unless launched with `--allow-file-access-from-files`, which breaks double-click-to-open, so this is a **generated merge**, not a live embed:

- **`_UI/build-design-studio.js`** (a small Node script; if Node isn't available where you're building, a behaviour-identical Python port is an acceptable stand-in — verify it byte-for-byte against a known-good `Design-Studio.html` before trusting it, the way this tool's own sessions have done) reads both `3_Massing/Massing-Studio.html` and `4_Space-Planning/Test-Fit-Studio.html`, prefixes Massing's shared DOM ids with `ms-` (Test-Fit's stay unprefixed), scopes each Studio's CSS under its own pane, rewrites viewport-relative CSS (`position:fixed`, `100vh`) to be pane-relative, and writes the result to `Design-Studio.html` at the project root.
- **Generated, never hand-edited.** Treat it exactly like any other build artifact: edit `Massing-Studio.html` or `Test-Fit-Studio.html`, then re-run the build script (or its verified equivalent) to regenerate `Design-Studio.html`. A hand-edit to the generated file will be silently lost on the next regeneration.
- **Build it once both Studios exist for a project** — a project with only one of the two (e.g. Test-Fit alone, no Massing built) has nothing to merge; skip this step and let each Studio work standalone until the other exists.
- **New shared ids need adding to the script's `SHARED_IDS` list explicitly** (an allowlist, not a blind rename) whenever a new feature adds a DOM id or literal `getElementById(...)` call that both files happen to reuse — check by grepping the *other* file for the exact name before shipping; this project has a documented history of exactly this class of collision.

## The Massing Studio (interactive instrument) — evolves the phase from *pick* to *steer*

Build a single self-contained HTML tool (`Massing-Studio.html`, Three.js + Chart.js from CDN) so the architect works the massing, not just reviews it. **Cost principle that governs what's built-in vs. on-request: anything that runs client-side in the browser is a one-time build then free forever; anything that needs the model in the loop on every use costs tokens each time.** Build the first kind in by default; gate the second kind behind an explicit ask.

### ALWAYS build in (client-side — one-time cost, then free)
1. **Steerable volumes + live driver read-out.** Volumes adjustable by sliders (E–W, N–S, width, depth, height, rotate-90, **base-elevation for stacking a room on a room**, and a **glazing % slider** 0/25/50/75/100). Glazing must feed the thermal proxies (glass ≈ 3.5× a wall's loss) — **but which way that cuts is climate-conditional, not universal.** In a temperate climate (this proxy's default assumption): a winter-thermal driver falls and a daylight driver rises with more glass — the real tension, live. Near the equator, that relationship inverts or goes flat: there's no winter heat-loss season to trade against, and more glazing (especially E/W-facing) is more often a *cooling/glare* liability than a winter-gain benefit — check `phase-2-site.md`'s latitude-conditional sun-study branch before trusting the default proxy direction on a non-temperate site, and flag the proxy `[proxy, unverified]` if the climate regime hasn't actually been confirmed. Support multi-storey via base-elevation with per-storey cap accounting (footprint-only coverage). On every change, recompute and display: a **cap meter** (dwelling floor vs. the hard program cap, red when over), coverage %, enclosed volume, façade/envelope area, build-simplicity (volume count), and **concept-grade driver proxies** (a geometric heuristic per driver + any project-specific gate like a cap-safety score). Label the proxies honestly as a live gut-check, not analysis — but wire them to the real drivers so the model *talks back*.
2. **Mandatory sun-tested section.** A 2D section cut (movable, both principal axes) drawn from the same geometry, with summer/winter noon sun rays at the site's computed altitudes and the key obstruction (neighbour ridge, forest wall) shown — so the sectional lessons from phase 1 (buffer-zone, roof daylight) are worked at massing, not deferred. Section is not optional; a massing with no section is half-done.
3. **Trade-space plot.** A small scatter/bubble chart placing every option on the two or three competing objectives the project actually trades (e.g. cap-safety × a signature driver, bubble = winter energy), with a **live point** that moves as the architect edits — so hybrids are seen relative to A/B/C and no driver is traded away invisibly.
4. **⤓ Export JSON — neutral interchange for downstream tools.** Beside the existing share-edits/export button, a button that emits `massing-interchange/v1` (schema of record: `Massing-Export-Roadmap.md` at the tool root) — the current scheme's boxes plus site header, structured for the Rhino/Revit/Blender receivers to consume without touching the Studio itself. Fixed shape, one-time build, no ongoing cost:
   - `axes`: x=East(+), z=South(+), y=Up, north is −z; box `x,z` = **SW corner** in plan (any rotation baked into `w`/`d`, not a separate flag).
   - `volumes[]`: `{id, type, x, z, w, d, h, base, glaz}` (+ `clerestory:true` where set).
   - `site`: `{origin, northDeg, latLong, lotPolygon, setbackPolygon, lotArea, storeys}`. **`latLong` is required, not optional** — pull it as the site polygon's centroid (or the geocoded site point, if the site phase already produced one) from `2_Site/data/*.geojson`; downstream solar/sun-study receivers (e.g. the Blender template+import pair under `_Export-Receivers/Blender/`) need real coordinates and have no other source for them. `storeys` is inferred from the distinct base elevations present in the current scheme, not fixed.
   - `program`/`metrics`: whatever the Studio already computes for the cap meter/coverage — pass the live numbers through, don't recompute.
5. **A "Save for Test-Fit sync" button**, additive alongside the existing Export JSON button (learned 2026-09-08, from the same disconnect a Fable-model take was asked to weigh in on: two Studios, no live connection, a hand-typed cap number in Test-Fit Studio drifting from the real massing). Writes the same `massing-interchange/v1` payload to a **real file** via the File System Access API (`showSaveFilePicker`, handle persisted in IndexedDB so repeat saves overwrite the same file without re-prompting) rather than an anonymous Downloads-folder file — this is the file Test-Fit Studio's "Sync from massing" button reads. **Deliberately a separate button, not a repurposing of the existing Export JSON download** — the Rhino/Revit receiver pipeline already depends on that button's exact current behaviour (a `nonimuss-massing-<scheme>.json` download), documented in `_Export-Receivers/Revit/01_Workflow-Quickref.md`; don't break a working, documented pipeline to add a new one. Feature-detects `window.showSaveFilePicker` and falls back to the existing download behaviour on browsers without it (Firefox/Safari).
6. **A "Room massing (live)" topbar mode**, alongside the default "Schematic (Stage 1)" mode — see "Room massing (live)" above for the full spec (one box per Test-Fit room, fed through the same `drawSection()`/cap-meter, live, never written to `state`). This is cross-phase like the merge below: it only does anything once both this Studio and phase 4's Test-Fit Studio exist for the project **and** share one runtime (`Design-Studio.html`, built by `_UI/build-design-studio.js` — see that section). Build the mode toggle in regardless; it degrades to "nothing to show" (or Test-Fit's own standalone fallback, phase-4) rather than erroring when the merge doesn't exist yet.

### OPTIONAL — offer, but run only on request (model-in-the-loop — real recurring token cost)
- **Sketch / napkin → option.** Architect uploads a hand parti; reconstruct it as measured geometry, score and critique it. Costs a vision ingest + reasoning every time — worth it, but ask first.
- **Architect-collaborator (multi-voice) mode.** Beyond the standard one-shot gate below: convene the standing three-voice roster — **Design Collaborator** (generative protagonist; calibrated to MacKay-Lyons + Safdie as sensibilities, not pastiche), **Client** (from the client profile), **Studio Critic** (~75% RAIC review / 25% DP+Code) — in escalating rounds that *always end with the Design Collaborator turning critique into dimensioned, testable moves*. Full spec in `references/collaborator-voices.md`. On-request / token-taxing; usable in any phase, not just massing.
- **Real-drawing precedent overlay.** Fetch and overlay actual precedent plans/sections at scale beside an option. Fetch + image ingest per precedent = expensive; a cheap *schematic* overlay redrawn from saved precedent cards is the low-cost substitute.

### Studio hygiene
Self-contained single file; syntax-check the script before delivery; sanity-check that the driver proxies reproduce the written narrative for each option (the strong option should score strong on the drivers you claimed). Keep a simpler orbit-only viewer if useful. Link the Studio from `Massing-Options.md`.

## Gate questions worth asking (standard, always run)
What breaks if the program grows 15%? Which option is most resilient to the top open question? Is the recommended option the best one or the safest one — and is that the right trade here? Plus the hardest question a reviewer will ask about the recommended parti.
